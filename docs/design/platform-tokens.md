# Platform tokens — the cross-platform contract

**Status:** implementation-grade specification
**Implements:** `docs/design/overhaul-plan.md` §6 (token-only exception to AGENTS.md §9.3 — no business logic crosses platforms, only colour/material tokens)
**Reads with:** `docs/design/material-modes.md` (the three modes and why), `packages/design-system/tokens.json` (the contract)
**Implemented by this wave:** `apps/mobile`, `apps/desktop`
**Specified here (not implementable in this repo):** iOS/SwiftUI, WinUI, macOS vibrancy

## 0. The one rule

> **`tokens.json` is the only place a colour is decided. Every platform reads it;
> no platform retypes one.**

| Artefact | Owner | Produced by |
|---|---|---|

## 1. Token roles: what a platform actually has to map

Two layers, and the split is the thing that keeps glass from spreading
(`material-modes.md` §2.0):

**Layer A — structure.** Opaque in **all three modes**. A platform maps these to
its ordinary colour types (sRGB `Color`, `SolidColorBrush`, CSS colour string).
They are never given alpha and never given a blur.

**Layer B — material.** Only the floating roles. These are the only rows whose
values change when the mode changes, and every one of them that can be
translucent ships a **paired `-solid` token**.

| Layer | Contract key | JSON location |
|---|---|---|
| A | `canvas` | `palette.structure.canvas` |
| A | `surfaceRaised`, `surfaceInset`, `surfaceRow`, `surfaceSunken` | `palette.structure.*` |
| A | `surfaceScrim` | `palette.structure.surfaceScrim` (translucent in every mode — see §3) |
| A | `surfaceOverlaySolid`, `surfaceNavSolid`, `surfaceSheetSolid`, `surfacePaletteSolid` | `palette.structure.*` |
| A | `borderDefault`, `borderStrong`, `borderFocus` | `palette.structure.*` |
| A | `textPrimary`, `textSecondary`, `textMuted`, `textInverse` | `palette.structure.*` |
| A | `accentPrimary`, `accentText`, `accentOnPrimary`, `success`, `warning`, `danger`, `info` | `palette.structure.*` |
| A | `statusPaid`, `statusPartial`, `statusUnpaid`, `statusOverdue`, `chart1`…`chart6` | `palette.structure.*` |
| B | `mat-blur`, `mat-saturate`, `mat-brightness`, `mat-translucent` | `palette.materials[mode].*` |
| B | `surface-overlay`, `surface-nav`, `surface-sheet`, `surface-palette` | `palette.materials[mode].*` |
| B | `surface-scrim` | `palette.materials[mode].*` |
| B | `mat-border-alpha` | `palette.materials[mode].*` |
| B | `mat-specular`, `mat-fresnel` | `palette.materials[mode].*` (CSS-only; §4.6) |
| B | `shadow-overlay`, `shadow-sheet` | `palette.materials[mode].*` |
| B | `mat-filter` | composed string; **web/Expo-web only** |
| B | `mat-native` | the frame colour a native backdrop takes (§5) |

**Invariant, enforced by `verify-tokens.mjs` in the design-system package:** the
material layer may only change the four translucent roles, the scrim, the border
alpha and the shadow ramp. `text*` and `accent*` are byte-identical across all
three modes, so **switching material can never change a contrast ratio.**

## 3. The alpha-bearing roles, and what each platform needs instead

Only these roles ever carry alpha. Every one of them has a paired opaque token in
`palette.structure`, and **the fallback is a value swap, never a branch in a
component** (`material-modes.md` §2.0).

| Role | Alpha by mode (`inked`, illustrative) | Fallback token | Native equivalent |
|---|---|---|---|
| `surface-overlay` | `1` · `0.15` · `0.34` | `surface-overlay-solid` | iOS: material + tint; WinUI: `AcrylicBrush.TintOpacity`; macOS: `NSVisualEffectView.material`; RN: `expo-blur` + `rgba` background; web: `color-mix()` |
| `surface-nav` | `1` · `0.15` · `0.30` | `surface-nav-solid` | iOS `.sidebar` material; WinUI `AcrylicInAppFillColorDefaultBrush`; macOS `.sidebar`; RN `expo-blur` behind a translucent bar |
| `surface-sheet` | `1` · `0.32` · `0.52` | `surface-sheet-solid` | iOS `.sheet` material; WinUI `AcrylicInAppFillColorBaseBrush`; macOS `.sheet`; RN `expo-blur` |
| `surface-palette` | `1` · `0.20` · `0.40` | `surface-palette-solid` | iOS `.regularMaterial`; WinUI `AccentAcrylic…` (`TintOpacity = 0.8`); macOS `.menu`; RN `expo-blur` |
| `surface-scrim` | `0.56` · `0.56` · `0.60` | **none — it is always translucent** | Smoke on every platform. Do **not** give it a solid fallback: a scrim that is not translucent is a dialog that leaks the screen behind it. |
| `mat-border-alpha` | `1` · `0.16` · `0.22` | `border-strong` | stroke opacity / `CardStrokeColorDefault` |

Two more alpha facts that bite on native:

- **`--mat-border-alpha` is a *stroke* alpha, not a fill alpha.** Do not feed it to
  a background.
- **The specular hairline and the fresnel sheen are CSS-only.** They are light
  interacting with a 2D surface. §4.6 says what native does instead.

## 4. The three modes per platform

### 4.1 Mode constants (mode-invariant; copied from `tokens.json`, never retyped)

| Contract value | `minimal` | `acrylic` | `liquid-glass` |
|---|---|---|---|
| `mat-blur` | `0px` | `40px` | `48px` |
| `mat-saturate` | `100%` | `125%` | `150%` |
| `mat-brightness` | `100%` | `105%` | `108%` |
| `mat-translucent` | `0` | `1` | `1` |
| `mat-border-alpha` | `1` | `0.16` | `0.22` |
| `surface-scrim` | `rgb(0 0 0 / 0.56)` | `rgb(0 0 0 / 0.56)` | `rgb(0 0 0 / 0.60)` |
| `shadow-overlay` | `0 8px 16px rgb(0 0 0/0.24)` | `0 8px 28px rgb(0 0 0/0.40)` | `0 12px 40px rgb(0 0 0/0.50), 0 2px 8px rgb(0 0 0/0.30)` |
| `shadow-sheet` | `0 32px 64px rgb(0 0 0/0.20)` | `0 28px 64px rgb(0 0 0/0.45)` | `0 32px 64px rgb(0 0 0/0.55)` |

`mat-saturate`, `mat-brightness` and the two blur radii are a **tuned port**,
not a published platform constant (`material-modes.md` §2.9). Treat them as a
tunable surface and record changes in the worklog.

### 4.2 iOS / SwiftUI — Liquid Glass is fully achievable here

| Mode | API | Fidelity |
|---|---|---|
| `minimal` | plain opaque views, `.shadow` from the shadow tokens, `Color` roles from §2 | **full** |
| `acrylic` | `.background(.ultraThinMaterial)` / `.regularMaterial`, or `.background(Material)` with `Color.surfaceNav` at the contract alpha | **full** (system material) |
| `liquid-glass` | `.glassEffect(.regular, in: .rect(cornerRadius:))`, `.tint(Color.accentPrimary)`, `.interactive()`, grouped in `GlassEffectContainer(spacing:)` | **full** |

```swift
// Minimal — the default on the five-screen Operate surface.
let card = RoundedRectangle(cornerRadius: 12)
    .fill(Color.surfaceRaised)
    .overlay(RoundedRectangle(cornerRadius: 12).strokeBorder(Color.borderDefault, lineWidth: 1))
    .shadow(color: .black.opacity(0.24), radius: 8, y: 4)

// Acrylic — a nav rail that shows content scrolling beneath it.
NavigationStack { … }
    .background(Color.surfaceNav)              // rgba from the contract
    .background(.regularMaterial)

// Liquid Glass — the floating affordances only, never a data row.
GlassEffectContainer(spacing: 24) {
    Button("Record Payment") { … }
        .glassEffect(.regular, in: .capsule)
        .glassEffectID("record-payment", in: namespace)
}
```

Native obligations, all of which the contract already answers:

1. **Group every glass view in a `GlassEffectContainer`.** Apple's own guidance:
   "applying too many effects to views outside of containers can degrade
   performance." At most two glass regions on screen
   (`material-modes.md` §5.2).
2. **Use the scroll edge effect** (`safeAreaBar(edge:alignment:spacing:content:)`,
   `scrollEdgeEffectStyle(_:for:)`) on any custom bar with content scrolling
   beneath it, instead of a hand-rolled alpha fade.
3. **Prefer `NavigationStack` / `TabView(style: .sidebarAdaptable)`** and let the
   system supply the material — "Reduce your use of custom backgrounds in controls
   and navigation elements."
4. **`glassEffect` needs iOS 26.** Below it, `.regularMaterial` is the closest
   and the app must not claim to be showing Liquid Glass.
5. Every toolbar icon needs an accessibility label (Rule 10).

### 4.3 WinUI — Acrylic/Mica brushes

| Mode | API | Fidelity |
|---|---|---|
| `minimal` | `SolidColorFill` + `ThemeShadow` + 1px `CardStrokeColorDefault` | **full** |
| `acrylic` | `AcrylicBrush` (`AcrylicInAppFillColorDefaultBrush`, `…BaseBrush`, `AccentAcrylicInAppFillColorDefaultBrush`) or `DesktopAcrylicBackdrop { Kind = DesktopAcrylicKind.Thin }` | **full** |
| `liquid-glass` | `DesktopAcrylicBackdrop { Kind = DesktopAcrylicKind.Base }` + `MicaBackdrop { Kind = BaseAlt }` for the base layer | **approximation** — Liquid Glass has no WinUI equivalent |
| scrim (all modes) | Smoke: translucent black, not mode-aware | **full** |

```xml
<!-- Minimal: the 95% case -->
<Border Background="{ThemeResource SurfaceRaisedFillColorDefaultBrush}"
        BorderBrush="{ThemeResource CardStrokeColorDefault}"
        BorderThickness="1">
  <TextBlock Foreground="{ThemeResource TextFillColorPrimary}" />
</Border>

<!-- Acrylic: a flyout, TintOpacity taken from the contract's mat-border-alpha -->
<Flyout>
  <Flyout.ChildTransitions>
    <PopupThemeTransition />
  </Flyout.ChildTransitions>
  <Border Background="{ThemeResource AcrylicInAppFillColorDefaultBrush}" />
</Flyout>
```

Rules carried from the WinUI documentation:

1. **Element-scoped system materials need `SystemBackdropElement`** (Windows App
   SDK **2.0+**). Below that a material only appears on `Window.SystemBackdrop`.
2. **Always set all four controller properties** — `FallbackColor`,
   `LuminosityOpacity`, `TintColor`, `TintOpacity` — per theme, because
   "After customizing any of the controller's four properties, it no longer
   applies default Light or Dark values." `FallbackColor` is the contract's
   `*-solid` role; that is not a coincidence.
3. **Mica is a base layer, applied once.** "Don't apply backdrop material more
   than once in an application", and it "will not appear on the element itself …
   only if all layers between the UI element and the window are set to
   transparent."
4. **Never put accent-coloured text over acrylic** — Microsoft says it is
   "likely to not pass minimum contrast ratio requirements at the default 14px
   font size". Use `accentText` over the canvas instead.
5. **Fluent elevation in WinUI:** Layer `1`, Control `2`, Card `8`, Flyout `32`,
   Tooltip `16`, Dialog `128`, Window `128`; contour stroke `1` at every level.
6. **Acrylic is GPU-intensive and auto-disables in Battery Saver**, which a web
   app cannot detect. The in-app Materials setting is the escape hatch.

### 4.4 macOS vibrancy (`NSVisualEffectView`)

| Mode | `NSVisualEffectView` | Fidelity |
|---|---|---|
| `minimal` | none — opaque `window.backgroundColor` | **full** |
| `acrylic` | `material: .sidebar` (nav) / `.headerView` (toolbar), `blendingMode: .withinWindow`, `state: .followsWindowActiveState` | **full at window level** |
| `liquid-glass` | `.popover` / `.sheet` / `.hudWindow` for the two floating roles | **approximation** — macOS vibrancy is the pre-Liquid-Glass material; it does not lens or morph |

```swift
// Nav rail. Vibrancy only on LEAF views: a parent that allows vibrancy cannot
// have it turned off by a subview, so this is a permanent styling decision.
let vibrancy = NSVisualEffectView()
vibrancy.material = .sidebar                 // by intended use, not by colour
vibrancy.blendingMode = .withinWindow        // toolbars/nav; .behindWindow for popovers
vibrancy.state = .followsWindowActiveState
vibrancy.isEmphasized = true                 // liquid-glass only
labelColor = NSColor.secondaryLabelColor     // matches --text-secondary
```

Rules carried from Apple's `NSVisualEffectView` documentation:

1. **Choose `material` by intended use**, not by the colour it happens to impart.
2. **Enable vibrancy only on leaf views.**
3. **Reduce Transparency (macOS → System Settings → Accessibility → Display →
   Reduce transparency) must force the material to `minimal`.** An app cannot do
   this implicitly; it has to read the OS preference or require the user to pick.
4. **Vibrancy works best with grayscale foreground content**, which is exactly
   what the Layer-A text tokens are.
5. **Where vibrancy must not be used:** any text-bearing data surface (tables,
   ledger rows, the roster, form fields), any scrollable list, and any view
   nested inside another vibrancy view. Those get the opaque structure tokens.

### 4.5 Android

**Android is covered by `apps/mobile`** — Expo/React Native is the Android
implementation of this contract, so this section points at that app rather than
duplicating it:

- palette + material: `apps/mobile/src/theme/tokens.ts` → `resolveTheme()`
- blur: `expo-blur`'s `BlurView`, with `intensity` computed from `mat-blur` by
  the generator (40px → 80, 48px → 96, `0px` → 0, i.e. clamped at 50px then
  doubled — a tuned port, computed once at generation time, never per render)
- tint: the palette `tier` (`dark` palettes get `tint="dark"`)
- alpha: the contract's own `rgba(...)` values applied as `backgroundColor`

**Material You / dynamic colour is deliberately NOT used.** Android's dynamic
palette is derived from the user's wallpaper; this product's palette is the
contract. Honouring both is impossible, and a tutor who picks "Inked" expects
Ink. If dynamic colour is ever wanted, it becomes a *fourth* mode alongside the
three, never a default.

`prefers-reduced-transparency` has no CSS surface on native, so the mobile app
reads `AccessibilityInfo.isReduceTransparencyEnabled()` and swaps the four
translucent roles for their `-solid` pairs in `resolveTheme(..., true)`.

### 4.6 What is *not* portable, stated once

| Role | Portable? | Why / what to use instead |
|---|---|---|
| Blur radius | partly | CSS/Expo take a radius; WinUI acrylic and AppKit vibrancy take **no** radius — the system picks it. Do not fight them with a fake value. |
| Saturation / brightness lift | no | Approximated by `saturate()`/`brightness()` on the web; on native it is a tint decision (`TintColor`/`LuminosityOpacity`), not a filter. |
| `mat-specular` (inner hairline) | no | It models light on a 2D surface. Native gets it free from the system material; where it does not, use a 1px `border-strong` stroke. |
| `mat-fresnel` (lens sheen) | no | Only `glassEffect` on Apple renders something like it. Elsewhere the honest answer is to leave it out. |
| `shadow-overlay` / `shadow-sheet` | partly | Every platform has elevation, but not the same numbers. Fluent's WinUI values are a better match than the CSS strings. |
| Refraction / lensing / pointer reaction | no | Needs per-frame geometry normals. Apple-native only. |

## 5. Tauri (implemented here) — Windows / macOS / Linux

The generated `src/theme/native.ts` holds this mapping as data, and
`src-tauri/tauri.{windows,macos,linux}.conf.json` are generated from it.

| Mode | Windows 11 | Windows 10 | macOS | Linux |
|---|---|---|---|---|
| `minimal` | none — opaque frame | none | none | none |
| `acrylic` | `mica` + CSS material in-webview | no Mica: `mica` is Windows 11 only, so Windows 10 falls back to the CSS layer | `sidebar` vibrancy | **none — `-solid` tokens** |
| `liquid-glass` | `mica` (Tauri exposes no `MicaKind.BaseAlt`/`Base`) | as above | `sidebar` (Tauri exposes no `isEmphasized`) | **none — `-solid` tokens** |

Hard constraints, from the Tauri config schema this repo validates against
(`apps/desktop/scripts/verify-tokens.mjs`):

1. `windowEffects` **"Requires the window to be transparent."** So the Windows
   and macOS platform configs set `"transparent": true`; the base config and the
   Linux config keep `false`.
2. `windowEffects` is **"Linux: Unsupported"**. `tauri.linux.conf.json` therefore
   contains **no** `windowEffects` key at all and pins the frame to the
   `--mat-native` colour — the fallback is explicit, not accidental.
3. `effects` may only name the 27 values in the schema's `WindowEffect` union.
   `state` and `radius` are **macOS-only**; `color` only affects
   `blur`/`acrylic` on Windows 10 v1903+ and does nothing on Windows 11.
4. **One backdrop per window.** Mica's own rule: "Don't apply backdrop material
   more than once in an application." Every in-webview material is therefore
   CSS, and at most two `.mat*` regions are on screen
   (`material-modes.md` §5.2).

### 5.1 The trade this wave records, and what is still unproven

- **macOS**: `transparent: true` requires `macosPrivateApi: true`, which uses
  private APIs — the desktop app then **cannot be submitted to the Mac App
  Store**. For a Tauri bundle (dmg) that is the right trade; if App Store
  distribution is ever required, drop `macosPrivateApi` and `transparent` from
  `tauri.macos.conf.json` and accept an opaque frame.
- **Not yet visible:** with an opaque `body` painting the canvas, Mica/vibrancy
  can only show through a region the document leaves transparent — today that is
  the title-bar drag strip in `src/shell/GlassShell.tsx`. Making the frame
  material genuinely visible is a shell task, not a token task, and it needs
  four things together: the transparency above, a transparent document root with
  the canvas painted *below* the strip, and the two `core:window:allow-set-*`
  Tauri permissions (`allow-set-effects`, `allow-set-background-color`) if the
  material mode should switch the native effect at runtime instead of at build
  time. Those permissions are **not** granted in this wave: `core:window:default`
  does not include them, adding capabilities is an auditable security decision
  (`AGENTS.md` §3.1), and nothing in the token contract needs them yet.
- **What was verified here:** the generated configs validate against the shipped
  `@tauri-apps/cli` schema; the desktop TypeScript compiles; `vite build`
  succeeds and the built CSS contains all 20 palettes × 3 materials. **What was
  not:** an actual `tauri build` (no Rust toolchain exercised in this
  environment) and a running window on any of the three platforms.

## 6. Accessibility fallbacks, per platform

The contract's guarantee is that legibility never depends on translucency. Each
platform needs a different trigger for the same three remaps.

| Trigger | Web / Tauri webview | iOS | Android | macOS | Windows |
|---|---|---|---|---|---|
| `prefers-reduced-transparency: reduce` | CSS media query (`index.css`) | `UIAccessibility.isReduceTransparencyEnabled` → force `minimal` | `AccessibilityInfo.isReduceTransparencyEnabled()` → `resolveTheme(..., true)` | Reduce transparency → `minimal` | Transparency effects off → `minimal` |
| `prefers-contrast: more` | CSS media query → `border-strong` + `text-secondary` | increase the `borderStrong`/`textSecondary` weights, or ship a high-contrast variant | `AccessibilityInfo` high-text-contrast where available | Increase contrast / darken materials | High Contrast |
| `forced-colors: active` | CSS media query → `Canvas`/`CanvasText`, `forced-color-adjust: none` | not applicable (no forced-colors mode) | `isHighTextContrastEnabled` → swap to the `-solid` layer | Increase contrast | **The High Contrast dictionary already proves the strategy**: every acrylic/mica key becomes a `SolidColorBrush` on `SystemColorWindowColor` — precisely our `--surface-*-solid` layer. |

Two rules that must survive any future platform work:

1. **The material block may only touch the four translucent roles, the scrim, the
   border alpha and the shadows.** If a new platform needs to change
   `textPrimary` for a mode, that is a contrast regression, not a material.
2. **A fallback is a value swap, never a `if (unsupported)` in a component.**
   Components reference the translucent role; the platform swaps the role's value
   once, globally.

## 7. How to add palette #21

**Never hand-edit a generated file.** The procedure:

1. **Add the scheme** to `packages/design-system/src/schemes.ts`: hue anchor,
   temperature, accent hue, tier (`dark`/`light`), the Figma scheme number and
   note. No hex values — the library publishes names and descriptions only.
2. **Regenerate and verify the contract:**
   `pnpm --filter @buddysaradhi/design-system emit`
   It runs the contrast gate and **writes nothing if any text role is < 4.5:1, any
   meaning-carrying border < 3:1, or two palettes collapse to the same hex.**
3. **Regenerate the mobile layer:** `node apps/mobile/scripts/generate-tokens.mjs`
   → `apps/mobile/tokens.css`, `tailwind-theme.generated.js`,
   `src/theme/tokens.ts`.
4. **Regenerate the desktop layer:** `node apps/desktop/scripts/generate-tokens.mjs`
   → `src/styles/tokens.css`, `src/theme/tokens.ts`, `src/theme/native.ts`, and
   the three `src-tauri/tauri.*.conf.json`.
5. **Verify both platforms:**
   `node apps/desktop/scripts/verify-tokens.mjs`
   It re-runs both generators and fails if any artefact is stale or hand-edited,
   validates every Tauri config against `@tauri-apps/cli`'s schema, checks that
   the effect names exist in the schema's union, and asserts that mobile and
   desktop emit **the same set of custom properties** (87 today).
6. **Typecheck both apps** (`tsc -p apps/mobile/tsconfig.json`,
   `tsc -b apps/desktop/tsconfig.json`). A new key that the generators emit but
   the hand-written consumers do not know about is fine; a key a consumer expects
   but the contract no longer has is a compile error, which is the point.
7. **The three detectors** must stay green: `tsc`, `oxlint` (desktop), and
   `node .agents/skills/impeccable/scripts/detect.mjs --json apps/mobile apps/desktop`.
8. **If the platform list is UI-facing**, add it to the Settings → Appearance
   picker. That is a rendering task: `PALETTES` and `MATERIALS` already carry
   `id`, `name`, `tier`, `figmaScheme` and three swatches.

**Adding a *material* instead of a palette** is the same three commands plus one
edit in `packages/design-system/src/material.ts` (`MATERIALS`), which both
generators read from `tokens.json` — the platform mapping tables in this document
are the only thing a new mode forces a human to update.

## 8. Judgement calls recorded by this wave

| Call | Decision | Why |
|---|---|---|
| Mobile palette switching | JS (`resolveTheme` + `style` props), not CSS attribute selectors | React Native has no `data-palette` selector to switch a stylesheet block, and RN's colour parser does not accept CSS Color 4 `rgb(r g b / a)`. The generated `-rgb` triplets keep the Tailwind opacity modifier (`bg-accent/20`) working for the class surface. |
| Mobile blur | `expo-blur` `BlurView`, radius→intensity computed in the generator | NativeWind has **no** backdrop-filter utility (its Effects list is blend mode, box shadow, opacity). A blur cannot be produced from a style. |
| Mobile appearance persistence | none yet | `@react-native-async-storage/async-storage` is not a dependency; inventing a storage key in a token wave would create a second unaudited place to choose a palette. |
| Desktop `@buddysaradhi/ui` | replaced with local `src/shell/Panel.tsx` and `Button.tsx` | That package still paints `bg-white/5`/`#00FF9D` and the retired glass tiers, and `packages/**` is outside this wave's scope. The dependency stays in `package.json`; only the desktop render path changed. |
| Desktop `transparent: true` on Windows/macOS | enabled, with the private-API note and the "not yet visible" caveat in §5.1 | It is the documented requirement for a native backdrop; without it the `windowEffects` entry is inert. |
| Tauri capability additions | **not** added | Nothing in the token contract needs runtime effect switching yet, and `core:window:default` does not grant `set-effects`. |
| Violet | mapped to the `accent` role | The contract has no violet semantic role, so `accent-violet` (`#B388FF`) is not expressible; a colour with no token role cannot be typed. |
| Duplicate generators | mobile and desktop each own a generator | A shared module would have to live in `packages/`, which no platform wave may touch. The parity invariant is asserted by `verify-tokens.mjs`. |
