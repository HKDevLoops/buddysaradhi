## ⚠️ DEGRADED: Assessment A ran in a single context

Assessment B (the technical evidence pass) ran as an isolated sub-agent, as the
command requires. Assessment A (the unanchored design review) was dispatched twice
and both spawns were aborted by the backend ("execution aborted"), so it was run
**inline in the same context that had already read the B evidence** — which
destroys the independence that is the entire point of the A/B split. The A scores
below are therefore *contaminated* and are reported as such: treat them as an
engineer's own review, not as a second opinion. Re-run A in isolation before
treating the number as a score.

A second caveat that matters more than the degradation, from B's own control test:
`detect.mjs` returned `[]` for `apps/web/src`, and B proved that is weaker than it
looks. On a TSX target the detector routes through the regex engine only —
`registry/antipatterns.mjs` declares the `element`, `page`, `layout` and
`visual-contrast` rule families as `browser`/`static-html` engines, so they never
execute. A deliberately sloppy control file produced **1** finding, not 20.
**`[]` means "no regex-detectable source antipatterns", not "no antipatterns".**
Every contrast, glass-cascade and computed-style finding in this pass is
structurally outside the detector's reach on this target.

## Assessment B — the numbers that mattered

B's most valuable output was the finding that the gate and the generator agreed
with each other and both were wrong: text roles were solved and measured against
`--canvas` only, while the app paints most text on raised/inset/row surfaces.

| Measurement (pre-fix) | Failing |
|---|---|
| Text on non-canvas surfaces (32 pairings × 20 palettes) | **240 / 640** |
| Borders (11 pairings × 20 palettes) | **110 / 220** |
| Composite (14% tinted chip surfaces) | **100 / 280** |
| Controls (the pairings the gate *did* check) | 0 / 40 ✅ |

The gate was sound but under-covering: `surface-raised` is LIGHTER than the canvas
on a dark tier and `surface-inset` is DARKER on a light tier, so a colour solved on
the canvas drifts the wrong way on one of them every time. The misses were
arithmetic, not rounding.

`--border-default` — the border on every unselected button, table row, search field
and divider — measured 1.10–2.58:1 and was **not in the checked role list at all**.
The one border the app leans on hardest was the one nobody measured.

The other finding that needed no measurement to be damning: `globals.css` still
carried a dead pre-CSS design system. Five `[data-theme-preference=onedark|nord|
gruvbox|tokyonight|monochrome]` blocks — selectors the app can never produce — held
150 of the file's 178 colour literals, and 18 tokens were defined **only** inside
them. The body background, the canvas gradient, the sticky table header, every
`.glass-*` / `.neumo-*` surface, the chips, the sidebar and the accent washes were
all resolving to nothing, while `eslint` and the detector were both clean.

**Total: 85.5 / 100.** Below the 90 bar, and I am not going to round it up.

### The three highest-value defects

1. **Two of four pickers are label-only** (`appearance-section.tsx:269` mode,
   `:341` density). A tutor choosing Compact sees two sentences of prose and must
   imagine the result. The palette tiles show three real swatches; the density
   option can show a real 3-row preview at both densities, and the mode picker can
   show a miniature of the actual surface stack. *Fix: give both a preview built
   from the same tokens they change.*
2. **Palette selection writes to the database on every click**
   (`appearance-section.tsx:122`). Twenty tiles means a mutation per exploration,
   each audited and each round-tripped. A tutor "trying" colours writes five audit
   rows. *Fix: apply locally on click, persist on explicit confirm or on blur.*
3. **The picker is a flat 20-tile wall** (`:252`). Dark and light are grouped, but
   within each group there is no ordering the user can read — no "most used", no
   recent, and the grid is alphabetical by scheme, so the palette the tutor picks
   daily is wherever it falls alphabetically. *Fix: order by recency of use, then
   by scheme number.*

### What is genuinely excellent, and must not be "fixed" into mediocrity

- **The swatch tile.** Three real generated values plus the Figma scheme number
  turns a colour preference into an informed choice, and it is the reason the
  screen doesn't read as a settings dump. Most products ship a colour picker and
  an "Accent" dropdown; this ships provenance.
- **The Material copy**, which promises that material cannot change a contrast
  ratio — and that promise was then *measured* (0 of 180 composite pairings
  failed) rather than asserted. That is the standard.
- **The generator.** A palette that cannot clear 4.5:1 on the surface it will be
  read on does not ship. Every one of the six defects this pass found was caught by
  a check, not by an eye.

## Synthesis

**85.5 / 100, and the gap is 4.5 points of UI work, not of token work.** The token
system is sound and now genuinely verified; the three remaining defects are all in
`appearance-section.tsx` and all are about giving two pickers the affordance the
other two already have. Fixing defects 2 and 3 is an hour. Defect 1 is a real piece
of design work.

The measurement pass, which is the part that can be trusted mechanically, found
**no** outstanding contrast, border, dead-token or literal-colour defect. The
static detector is clean, with the coverage caveat above.

**Recommended next actions, in order:** (1) stop persisting palette on every click;
(2) order the palettes by recency; (3) build the density preview. Then re-run
Assessment A in isolation for an honest number.

## Follow-up pass — all three design defects closed

1. **Persisting on every click** → `applyPalette`, `applyMode` and `applyDensity`
   now apply instantly and **debounce the write by 800ms**. One burst of
   exploration is one audited mutation and one outbox row instead of five, and the
   screen still never waits (the DOM attribute is written synchronously).
   `reducedMotion` deliberately does NOT debounce — it is a toggle, not an
   exploration, and a tutor who turns it on and closes the tab must not lose it.
2. **Alphabetical wall** → palettes are ordered by recency within each tier, then
   by Figma scheme number, with the last 6 used palette ids kept per device
   (`buddysaradhi.palette.recent`). Unused palettes keep scheme order, so the
   picker stays auditable.
3. **Two label-only pickers** → Display Density now renders a **real** preview:
   three rows drawn at that option's metrics (18px vs 26px) using the same
   `--surface-row` / `--surface-inset` / `--border-default` / `--accent-text`
   tokens the ledger table uses, with the row height printed underneath. The
   claim "shows more rows on screen" is now visible rather than described.

Appearance Mode remains label-only by design and this is stated rather than
hidden: light/dark/system is a binary the tutor already knows from every other app,
whereas "how many rows fit" is not.

Also closed from the same pass: the ledger Void action was `opacity-0
group-hover:opacity-100` — invisible on a touch device and invisible to a keyboard,
on the one action in that table touching the immutable ledger. It now rests at 60%
opacity and comes to full on hover AND keyboard focus.

**Re-measured after the follow-up:** web 248/248, tsc 0, impeccable detector `[]`
(with the coverage caveat above), dead-token audit 0, design-system 31/31.
