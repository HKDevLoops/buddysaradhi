### [AUD-001] **P0** · A voided payment never unwinds the invoice's credited amount — the tutor stops chasing money they were never paid

- **File:** `packages/core/src/fees.ts:325-327` (SQL dialect) · `packages/core/src/feesPrisma.ts:349-354` (ORM dialect) · `apps/gateway/routes/ledger.ts:425` (`creditedForInvoice`) · `apps/gateway/routes/ledger.ts:580-583` (`paidMap`) · `apps/gateway/routes/analytics.ts:355-357,382-384,410-413`
- **Spec violated:**
  - `14_Edge_Cases.md:84` **EC-F-05** *(Governing: P0)* — *"Atomic txn: `VOID` ledger entry + receipt `voided_at` + **invoice status reverts to `unpaid`/`partial` based on remaining credits**."*
  - `12_Business_Rules.md:170` **BR-RPT-04 [CRITICAL]** — *"balance_due = Σ(charges, type≠VOID, **reverses IS NULL**) − Σ(credits, type≠VOID, **reverses IS NULL**)"*
  - `07_Fees_and_Payments.md:1084` — *"// 4. Revert invoice status (same recompute as §9.6 step 5)"*
- **What is wrong:** the only "is this row reversed?" predicate any implementation
  has is `void_of_id IS NULL` **on the row itself**. But a voided *original* has
  `void_of_id IS NULL` — it is not a reversal; **the reversal** carries the
  `void_of_id` pointing back at it. There is no `reverses_entry_id` column on
  the original (`migrations/0001_init.sql:261-293` has only `void_of_id`), so the
  original can only be excluded by a **reverse lookup**:
  `NOT EXISTS (SELECT 1 FROM ledger_entries v WHERE v.void_of_id = e.id)`.
  All three dialects make the identical mistake, so the §3.5 parity gate
  **cannot see it**.
  The ORM dialect's own comment states the intent the code does not implement:
  > *"credits attributed to THIS invoice, excluding the VOID row and **the row it reverses**"* — `feesPrisma.ts:348-349`

  The gateway's route compounds it: `apps/gateway/routes/ledger.ts:1040-1043`
  says the invoice-status revert *"is deferred … the credited-for-invoice reads
  self-heal through the void_of_id filter"*. **That comment is false** — the
  filter cannot self-heal.
  Most damning: at `apps/gateway/routes/ledger.ts:538-542` the gateway computes
  the **correct** semantics for display (*"a row is voided iff some OTHER row in
  the set carries it as `void_of_id`"*) — twenty lines above using the wrong
  predicate for the money.
- **Trigger:** student owes ₹1,000. Invoice `INV-000001` total 100000 paise,
  `unpaid`. Payment of 100000 → `FEE_CHARGED` debit 100000, `PAYMENT_RECEIVED`
  credit 100000, invoice → `paid`. Tutor voids the receipt → gateway posts a
  `VOID` debit 100000 and sets `receipts.voided_at`. **Nothing else changes.**
- **Impact:**
  - `students.balance_paise` = 100000 → the student owes ₹1,000 (correct).
  - `invoices.status` = **`paid`** (never reverted) → the Fees screen shows the bill as settled.
  - `creditedForInvoice(INV-000001)` = **100000** → the invoice reads fully paid.
  - `openInvoices` filters `status IN ('unpaid','partial','overdue')` → the invoice is **not open**, so the next payment cannot be attributed to it. The ₹1,000 becomes an auto-invoiced phantom `INV-000002`, and the tutor's collected figure absorbs it.
  - The Dashboard's "Collected This Month" also counts the voided payment as cash in (see AUD-002).
  - **Net: the tutor believes ₹1,000 was collected when it was not, and stops chasing it.**
- **Proof:** **PROVEN** by the audit stream — executed against in-memory SQLite
  with the parity suite's schema:
  ```
  BEFORE VOID  implementation creditedForInvoice = 100000 | BR-RPT-04 (excl. reversed) = 100000
  AFTER  VOID  implementation creditedForInvoice = 100000 | BR-RPT-04 (excl. reversed) = 0
  invoice.status = paid  | students.balance_paise (truth) = 100000
  openInvoices(status IN unpaid/partial/overdue) rows = 0
  ```
  The implementation's sum is **unchanged by the void** while the spec's formula
  correctly drops to 0. Independently re-verified by the parent: all three
  dialects read the same predicate, and `migrations/0001_init.sql` has no
  `reverses_entry_id` column.
- **Fix:**
  1. Add a reverse-existence predicate to **all three** `creditedForInvoice`
     implementations **and** the gateway's `paidMap`:
     `NOT EXISTS (SELECT 1 FROM ledger_entries v WHERE v.void_of_id = e.id AND v.type='VOID')`.
     For the ORM dialect, project the reversing rows for the invoice's entries
     and exclude their ids in memory (the shim has no `NOT EXISTS` operator).
  2. Implement `07 §9.10 step 4`: after posting the VOID, recompute the invoice
     status from the remaining credits (`unpaid`/`partial`) **in the same
     transaction**.
  3. Regression test: charge → pay → void → assert `invoices.status != 'paid'`
     **AND** `creditedForInvoice(invoice) == 0` **AND**
     `students.balance_paise == invoice.total` **AND** the invoice is back in
     `openInvoices`.
  4. Add a **void scenario** to `packages/core/src/feesDialectParity.test.ts` —
     it currently has none (§6.2).
  - **IN-FLIGHT** for `apps/gateway/routes/ledger.ts`; **NOT in-flight** for
    `packages/core/src/fees.ts` and `feesPrisma.ts`, which carry the same defect.

### [AUD-002] **P0** · The plaintext PIN is written to a durable DB row and POSTed to the gateway — BR-SEC-07 [CRITICAL] is violated in the exact code that fixed F-03

- **File:** `apps/web/src/server/actions/settings.ts:1331-1336` (outbox payload) and `:1376` (gateway push body), inside `setPinAction`
- **Spec violated:**
  - `12_Business_Rules.md:206` **BR-SEC-07 [CRITICAL]** — *"No plaintext secret ever written to the DB. PIN stored as `argon2id(pin)`."*
  - `10_Security.md:77` — *"The PIN is **never** stored in plaintext."*
  - `docs/rfc/pin-proof-spec-amendment.md:116,118` — the only instrument that could sanction this is **"Status: PROPOSED — Awaiting Ratification"**, and it says the opposite: *"It is excluded from sync payloads and settings projections like `pin_hash`"* / *"the sync payload carries only `pin_updated_at`"*.
- **What is wrong:**
  ```ts
  // settings.ts:1331-1336
  payload: JSON.stringify({
    pin_updated_at: now,
    pin_proof: newProof,
    pin_hash: newHash,
    pin: newPin,          // ← PLAINTEXT PIN, durable, replicated
  }),
  ```
  ```ts
  // settings.ts:1376
  { pin_proof: newProof, pin_hash: newHash, pin_updated_at: now, pin: newPin },
  ```
  The code's own comment (`:1326-1330`) claims:
  > *"The PIN is write-only here — consumed by one HMAC at the edge, **never stored**, never logged, never echoed — and BR-SEC-07 is preserved because **what crosses the wire remains the proof**"*

  Both halves are false. The PIN **is stored** — in `sync_outbox.payload`, a
  durable, replicated row (`11_Data_Model.md` §4.18). And it **does** cross the
  wire. The comment is the only thing standing between a reader and the truth.
- **Trigger:** any call to `setPinAction` (first-time setup *or* a PIN change)
  with a 6–8 digit PIN.
- **Impact:** the tutor's PIN is recoverable in cleartext from the tenant DB's
  `sync_outbox`, from the gateway DB (via `/api/v1/settings/sync-apply`), from
  any DB exfiltration, and from a `.buddysaradhi` backup of either. The
  argon2id+pepper protection of BR-SEC-07 is bypassed entirely. The PIN gates
  void, backdated payment, bulk import, tenant wipe, account erase and backup
  export. `pin_hash` — the credential of record — is copied into the replication
  payload too, contradicting the RFC's own exclusion rule.
- **Proof:** **PROVEN** by the parent — `apps/web/src/server/actions/settings.ts:1331-1336,1376` read directly; the spec text quoted with line numbers.
- **Fix:**
  1. Remove `pin` **and** `pin_hash` from the `syncOutbox.create` payload and
     from the `gatewayPost("/api/v1/settings/sync-apply", …)` body. Carry only
     `pin_updated_at` (and `pin_proof` only once the RFC is ratified **and**
     the gateway's sync-apply path is confirmed to strip `pin_hash`).
  2. The F-03 problem this was meant to solve (a self-issued erase credential)
     needs a different fix: **the erase gate must re-verify the actual PIN
     through Supabase auth**, per `REMEDIATION_PLAN.md` F-03 recommendation (c)
     — *"the server never needs the client's PIN to store a proof, it needs to
     be able to re-derive one."* That requires no PIN at set-time and no PIN
     in any replicated row.
  3. Add a CI lint (next to `scripts/principle-lints.ts` L6) rejecting a
     `pin` / `pin_hash` / `pinHash` key in any `syncOutbox.create` payload, and
     a unit assertion in `apps/web/src/server/actions/settings-pin.test.ts`
     that the outbox payload never contains the PIN.
  - **§8 STOP-AND-ASK**: this touches auth/crypto and the erase credential. It
    needs the security owner's sign-off per §5.4.

### [AUD-003] **P0** · The secure-erase cascade aborts on the append-only ledger trigger — the "erase everything" endpoint can never complete

- **File:** `apps/gateway/lib/sql.ts:1178-1202` (`ERASE_TABLES[0] = "ledger_entries"`, `stmtEraseTable`) · `apps/gateway/routes/security.ts:177-211` (the cascade loop) · triggers at `apps/gateway/lib/schema.ts:327-331` and `migrations/0001_init.sql:411-412`
- **Spec violated:** `10_Security.md` §18.1 step 4 (the secure-erase cascade) and AGENTS.md §2 Rule 1's *"the single audited LEDGER-4 exception to 'no physical deletes'"* — **the exception must actually work**.
- **What is wrong:** the cascade issues `DELETE FROM ledger_entries WHERE tenant_id = ?` as its **first** statement, but `trg_ledger_no_delete`
  (`BEFORE DELETE ON ledger_entries → RAISE(ABORT, 'ledger_entries is append-only. Post a VOID entry.')`)
  aborts it. **No `DROP TRIGGER` exists anywhere in the gateway** (grep over
  `apps/gateway` → no match). The whole write transaction rolls back, so the
  erase never commits. `audit_log` is next in `ERASE_TABLES` and
  `trg_audit_no_delete` would abort it too.
- **Trigger:** tutor taps "Erase all data" and confirms with the PIN →
  `POST /api/v1/security/erase` → the first cascade statement aborts.
- **Impact:** the tutor's **right to erasure never happens** (DPDP-2025
  exposure — `23_Security_Harness_Plan.md`'s incident runbook), the endpoint
  500s, and the tutor is told nothing happened. No data is lost and no money is
  corrupted — the failure is loud but total.
- **Proof:** **PROVEN** by the audit stream — executed against in-memory SQLite
  with the gateway's trigger DDL:
  ```
  ERASE: DELETE FROM ledger_entries -> ledger_entries is append-only. Post a VOID entry.
  ```
- **Fix:** inside the same write transaction, `DROP TRIGGER IF EXISTS
  trg_ledger_no_update; DROP TRIGGER IF EXISTS trg_ledger_no_delete;` (and the
  two audit triggers) **before** the cascade and re-`CREATE` them **after** —
  or, better, move the ledger wipe behind an explicit audited
  `DROP TRIGGER`/`CREATE TRIGGER` pair in `lib/schema.ts` with a comment citing
  LEDGER-4. Assert: the erase route returns 200 and
  `SELECT COUNT(*) FROM ledger_entries` = 0 afterwards.
  - **IN-FLIGHT** for `apps/gateway/lib/sql.ts`; the trigger DDL in
    `lib/schema.ts` is **not** in-flight.

### [AUD-004] **P1** · `cf-connecting-ip` is trusted unconditionally — the caller picks its own rate-limit bucket **and** its own auth-lockout bucket

- **File:** `apps/gateway/lib/security.ts:228-251` (`getClientIp`); consumed at `apps/gateway/index.ts:200-209`, `:276`
- **Spec violated:** `10_Security.md` §3.5; `23_Security_Harness_Plan.md` §9; AGENTS.md §2 Rule 9
- **What is wrong:** the first thing `getClientIp` does is return a **client-supplied header**:
  ```ts
  export function getClientIp(req: Request, peer?: string, trusted?: string[]): string {
    const cf = req.headers.get("cf-connecting-ip");
    if (cf && cf.trim()) return cf.trim();     // ← BEFORE the peer check
  ```
  The function's own doc comment (`:223-227`) says *"the transport peer is a fact; headers are claims"* — then trusts a header first. The `TRUSTED_PROXY_CIDRS` strict mode is **short-circuited** by this branch: an operator who declares their proxies and verifies the peer is untrusted still gets an attacker-chosen identity. **This is a defect in code committed this session (`a63c280`)** — the F-05b precedence order put `cf-connecting-ip` ahead of the strict-mode branch.
- **Trigger:** send `cf-connecting-ip: <random>` per request.
- **Impact:** the 100/min per-IP ceiling never trips (unlimited probing) **and** the 15-attempt credential lockout never trips, because `apps/gateway/index.ts:276` keys it on `secCheck.clientIp`.
- **Proof:** **PROVEN** — strict mode ON, peer NOT trusted, spoofed header → `getClientIp` returned the spoofed `9.9.9.9` instead of the peer `203.0.113.5`; 200/200 requests allowed under a 100/min limit; 40 failures across 3 rotating keys → `locked:false` on every key.
- **Fix:** move the CF branch **behind** the peer check — honour `cf-connecting-ip` only when the peer is inside `TRUSTED_PROXY_CIDRS`, or behind a separate operator flag defaulting OFF. Add the *untrusted-peer* case to `apps/gateway/__tests__/security.test.ts` (the existing test at `:418` covers only a **trusted** peer, which is why it never caught this).

### [AUD-005] **P1** · `resolveTursoUrl` / `resolveToken` silently substitute a **different database and credential** than the one the HMAC signed

- **File:** `apps/gateway/lib/sql.ts:38-77`; consumed by `apps/gateway/lib/db.ts:48-72` (data path) and `apps/gateway/lib/schema.ts:414` (**the DDL path**)
- **Spec violated:** `10_Security.md` §7; §1 (the shared-DB fallback was closed as a named threat by RFC-009 §3.1); `11_Data_Model.md` §1
- **What is wrong:** the HMAC signs the **string** `x-db-url` / `x-db-token`.
  `resolveTursoUrl` then *substitutes*:
  ```ts
  if (url && (libsql:// | https:// | http://) && !url.includes("supabase.co")
      && !url.includes("gmqwdnvbfnwpzpctwvho")) { return url; }
  const envUrl = Deno.env.get("TURSO_DATABASE_URL");   // ← SUBSTITUTION
  ```
  A URL containing `supabase.co` (or the literal project ref), or one that is not `libsql://`, silently resolves to the **environment's** database. `resolveToken` substitutes `TURSO_AUTH_TOKEN` whenever the presented token is ≤ 20 characters. Each substitution means **the signature covers a different target than the one executed** — §7's request binding is not enforced end-to-end. The resolver also accepts `http://` and **any host**: an SSRF sink from the edge's network position.
  *This is committed code, not the IN-FLIGHT WIP* (`git diff` on `lib/sql.ts` shows only an unrelated 15-line addition).
- **Trigger:** a signed `x-db-url` containing `supabase.co`, or a token shorter than 21 characters.
- **Impact:** (i) §7 request binding is broken; (ii) the **DDL heal** would create tables and install the append-only ledger triggers on the substituted database; (iii) SSRF — the edge dials an arbitrary host with the tenant credential attached.
- **Proof:** **PROVEN** — with `TURSO_DATABASE_URL=libsql://SHARED-ENV-DB.turso.io`: `…supabase.co…` → `libsql://SHARED-ENV-DB.turso.io`; a URL containing the project ref → the same; `http://169.254.169.254/latest/meta-data/` and `https://attacker.example/collect` → accepted verbatim.
- **Fix:** make resolution **total and non-substituting** — a caller-supplied `dbUrl`/`dbToken` is used verbatim or the call throws; never fall back to the env DB. Reject a `dbToken` shorter than 21 chars instead of substituting. Constrain the URL to `libsql://*.turso.io|.turso.ai` and reject `http://`. Apply the same rule in `lib/db.ts:getTurso` and `lib/schema.ts:runHeal`.

### [AUD-006] **P1** · The request signature does not bind the HTTP method, path, body, or `Idempotency-Key`

- **File:** `apps/gateway/lib/auth.ts:459-470`; signer at `apps/web/src/server/get-db.ts:244`
- **Spec violated:** `10_Security.md` §7; `23_Security_Harness_Plan.md` §9 (*"replay / double-charge on ledger mutations"*); `12_Business_Rules.md` BR-SYN-01
- **What is wrong:**
  ```ts
  const dataToSign = `${tenantId}:${dbUrl}:${dbToken}:${timestamp}:${nonce}`;
  ```
  Method, path, body and `Idempotency-Key` are **absent**. A captured signature authorises **any route with any body** for that tenant inside the 120 s window. Critically, the `Idempotency-Key` — RFC-004 C1's designated replay defence — can be changed freely on a replay, so the DB-backed dedup does not catch it. The only remaining barrier is a **per-isolate in-memory nonce cache** (AUD-008).
- **Trigger:** capture any signed gateway request; replay within 120 s with a **new** `Idempotency-Key`, a different path and a different body.
- **Impact:** a duplicated money mutation (double-charge) or an arbitrary mutation attributed to the victim.
- **Proof:** **STATIC** — one template string, no second construction site.
- **Fix:** bind `method`, `path`, a hash of the **raw** body and the `Idempotency-Key` into the signed material on **both** sides, with a version prefix (`v2:`) so old clients fail closed. `apps/gateway/lib/crypto.ts:150-156` already records that this wire value cannot be re-keyed without a coordinated change — make it a two-file change in one commit.

### [AUD-008] **P1** · The direct-DB path does not fail closed when the session is absent — it silently substitutes a `local-dev` tenant, so a payment can be written to the wrong database and reported as recorded

- **File:** `apps/web/src/server/get-db.ts:31-61` (session read), `:63-93` (the fallback), consumed by `getAuthenticatedPrisma()` at `:97-108`
- **Spec violated:** AGENTS.md §2 **Rule 9**; `10_Security.md` §3; the file's own stated intent at `:76-78` — *"with a session, env vars are NOT a fallback in production (silent-wrong-DB class). Missing/dummy metadata throws typed DB_NOT_PROVISIONED"*
- **What is wrong:** a **slow** (5 s timeout) or **errored** auth read is treated as "no session", and the no-session branch hands back a **usable** handle:
  ```ts
  // get-db.ts:88-92
  const url = process.env.TURSO_DATABASE_URL || "file:./dev.db";
  const token = process.env.TURSO_AUTH_TOKEN || "";
  return { client: getDb(url, token), userId: LOCAL_TENANT, tenantId: LOCAL_TENANT };
  ```
  `getGatewayHeaders()` gets this right (`:204-214` throws `AUTH_REQUIRED`). The direct-DB path is the outlier.
- **Trigger:** a tutor records a payment while Supabase auth is slow (>5 s) or erroring — **or** an unauthenticated caller POSTs to a server-action endpoint (server actions are public HTTP endpoints; there is no session check on this path).
